# Retrieval Protocol

面向整个知识库的 LLM 检索协议。知识库的导航结构：

```text
wiki/index.md                   扁平目录（人读入口）
wiki/meta/agent-tree.md         Agent 检索第一跳：signpost 索引（publish_wiki.py 确定性生成）
wiki/meta/knowledge-tree.md     人读导航树：主题优先嵌套全貌（publish_wiki.py 确定性生成）
wiki/meta/research.md           按问题类型分组的全局开放问题/研究空白清单（publish_wiki.py 确定性生成）
wiki/topics|sources/            分支页面与叶子小节
```

`agent-tree.md` 是 Agent 检索的渐进式披露入口：只含领域名与主题
signpost（一句话摘要）及未归入主题的论文，**不含叶子明细**。检索从它开始，
逐层下降——先读 signpost 选分支，再打开候选页面，页面内部再按小节钻取。
这是 PageIndex 式"树索引 + LLM 树搜索"在本知识库的落地：索引由确定性脚本
维护（零 LLM 成本），检索时才消耗 LLM 判断，且只为展开的分支付出读取成本。

`knowledge-tree.md` 是人读导航视图：主题优先嵌套全貌（每个主题节点带摘要，
其论文、开放问题与研究空白嵌套其下，未归属论文单独分组，文末带按主题分类
视图）。普通定向问答不需要读它，survey 需要领域全貌时可读。

`research.md` 与树中开放问题/研究空白是同一批 topic 页
条目的两种透视（主题嵌套 vs 领域平铺），不是数据冗余；单一事实来源在
topic 页的 `## 开放问题` 与 `## 研究空白与候选方向` 小节。知识树中嵌套在
主题节点下的条目不再重复"来源"后缀，research.md 的领域平铺条目保留来源链接。
两个文档都只聚合**仍开放**的条目：被后续论文回答/填补的条目由发布器移入
topic 页的 `## 已解决的问题` / `## 已解决的研究空白` 归档小节，不再出现在
树与仪表盘中；检索时若在聚合视图里找不到某空白，先查对应 topic 页的归档小节。

## 第一跳：选择分支

1. 读 `wiki/meta/agent-tree.md`（不存在时读 `wiki/meta/knowledge-tree.md`，
   再退到 `wiki/index.md`）。
2. 只读 signpost 选分支：按领域定位，再按各主题的一句话摘要选出候选主题
   （不超过 3 个）；不要在这一跳展开任何页面。
3. 打开候选主题页的相关小节（topic → 概述 / 关键发现 / 开放问题），或直接
   打开未归入主题的 source 页；需要证据细节时沿 `[Paper: PDF p.X]` 指针进入
   source 页对应小节。
4. 用问题文本匹配节点：领域名、主题标题与摘要、页面标题、别名（agent-tree
   不含开放问题/研究空白文本；需要按问题文本匹配时，读 research.md 或
   knowledge-tree 的对应条目）。
5. 选出候选分支后，打开页面文件核实，不得仅凭树里的摘要断言页面内容。
6. 索引可能滞后于最近一次发布；找不到入口时，列出对应目录下的文件再判断。

`wiki/meta/research.md` 只在"按问题/空白选题"类查询时读（例如"这个领域还有
哪些研究空白可做"、"哪些开放问题未被回答"）：它一次给出全库的开放问题与
研究空白清单，无需先定位领域。普通定向问答与查证不读它——knowledge-tree
已含同样条目。

## lookup 模式：定向问答与查证

预算导向的剪枝下降，用于单点问题：

1. 读树，选不超过 3 个候选分支；
2. 只读候选页面的相关小节：topic → 概述 / 关键发现 / 开放问题；
   source → 对应编号小节；
3. 需要证据细节时，沿 `[Paper: PDF p.X]` 指针进入 source 页对应小节；
4. 回答必须带来源（页面 wikilink + 证据指针）。

页面预算默认不超过 5 个页面文件；问题复杂或用户要求时按需扩大，
并在回答中说明扩大理由。空结果如实报告"知识库中未见"，不编造。

## survey 模式：综述与专题深读

按用户声明的范围广度优先下降，无固定页数上限：

1. 确认范围：一个领域分支、一个主题，或整库（范围未声明时先询问）；
2. 读该范围内全部 topic 页：概述、论文与方法对照、关键发现；
3. 按对照表逐行钻取 source 页相关小节，验证关键数字与边界；
4. 每读约 5 页，把中间笔记写入 `work/survey-notes.md`（对话外文件），
   保护主会话上下文；
5. 最终综合逐条带来源指针，区分 共识 / 单篇主张 / 分歧 / 空白。

survey 的边界是用户声明的范围本身，不是固定页数；这正是它与 lookup
的区别——综述需要整树展开，而问答需要剪枝。

## 与空白挖掘的边界

survey 模式是只读检索：产出问答或综述，不回写 wiki。跨组或全库的研究
空白与候选方向挖掘（读 + 产出候选 + 用户确认后写回）由 `wiki-gap-mining`
skill 承担：读侧复用本协议的 survey 纪律（含归档小节），写侧仍走
`publish_wiki.py`。用户要综述或查证时走本协议；用户要挖空白、找选题或
综合已解决问题时路由到 `wiki-gap-mining`。

## 共享纪律

- 每个结论带页面链接与证据指针，可追溯到原文。
- 判断"页面不存在"前，先查树的别名与 index 条目（同名不同译是常态）。
- 树与 index 由 `publish_wiki.py` 维护，检索方只读不写。
